# 意图：让护栏在关键处真正有强制力，而不是靠 Agent 自觉

## 为什么做（给谁、解决什么痛点）
- 负责人（一人公司老板）只守 G1/G2/G3 三道关，其余全交给 Agent。前提是"Agent 想越界时会被机器拦下"。
- BOOTSTRAP 第 1–3 步实测发现，有几处关键位置拦不住，只能靠 Agent 自己不去做：
  - 合并：本机 gh 用的是负责人的管理员令牌，而分支保护对管理员不生效，Agent 可以不过检查直接合并 main。
  - `guardrail-ok`：Agent 可以通过 REST 接口自己加这个标签，CI 只看有没有，不看是谁加的。
  - 读密钥：只拦了几个常见的查看命令，换一个命令读就不拦，而且这一类没有 CI 兜底。
- 同时有三处误拦只读命令，会让 Agent 在正常工作中频繁停下来问人，打扰负责人。
- P0 开始后 Agent 会大量改代码，这些漏洞越早补越好。

## 做成什么样算成功（可观察的结果）
- Agent 在本机执行合并 main 的任何方式（`gh pr merge`、REST 接口、直接 push），在检查没过时都无法成功
- 一个不在 `owners` 名单里的账号给 PR 加上 `guardrail-ok`，CI 的 `guardrails` 检查仍然失败，并说明原因
- 读密钥文件的常见 shell 写法（`sed`、`grep`、`awk`、`python`、`node`、重定向等）在本地被拦下
- 之前误拦的三类只读命令能正常执行，同时原有的 15 个钩子测试全部仍然通过（只追加测试，不改已有测试）
- 弄清 CodeBuddy IDE 是否执行钩子返回的"询问"；如果不执行，有明确的降级方案并写进测试
- AI 审查评论只包含报告本身
- `npm run verify` 全绿

## 约束
- 只改护栏文件（`policy/`、`scripts/hooks|lib|checks|ci/`、`.github/workflows|prompts/`）和 `tests/`；PR 需要你本人加 `guardrail-ok`
- 规则引擎只依赖 Node 内置模块，Windows（Git Bash）/ macOS / Linux 行为一致
- 本地钩子和 CI 继续共用同一份规则（`scripts/lib/policy.mjs`）
- 不放松任何现有拦截；每处改动都要有钩子测试覆盖
- 时间：1–2 天

## 不做什么（防止范围膨胀）
- 不做完整的 shell 解析器或沙箱。本地 shell 规则是"尽量拦住常见写法"，最后一道防线仍然是 CI 和分支保护
- 不防负责人本人：你始终可以在 GitHub 网页上改设置
- 不改 G1/G2/G3 流程本身，不动 `apps/ packages/ packs/ mcp/`，不开始 P0

## 已确认的决定（G1，2026-10-13）
1. **合并绕过**：选 (b)。本机 gh 改用 Agent 专用、没有管理员权限的令牌，负责人的管理员令牌从这台机器上退出；`enforce_admins` 保持 `false`，负责人在网页上合并不受影响。

3. **"询问"不生效时**：如果 CodeBuddy IDE 不执行钩子返回的"询问"，降级为"拦截并提示找负责人本人"，与 Cursor 现在的做法一致。
